# CLAUDE.md — Frontend

This file provides guidance to Claude Code when working in `frontend/`.
Read the root `../CLAUDE.md` first for shared context (project overview, Sleeve model, monorepo layout).

## Tech Stack

React 18 + TypeScript + Vite · Tailwind · TanStack Query · React Router v6 · Recharts · Axios · openapi-typescript

## Commands

Run from `frontend/`.

```bash
npm run dev           # dev server at http://localhost:5173
npm run build         # tsc + vite build
npm run lint          # eslint
npm run gen:api       # regenerate src/api/schema.d.ts from ../openapi.yaml
```

`npm run gen:api` must be re-run after any backend `openapi.yaml` change. `frontend/openapi.yaml` is a generated artifact — never edit it by hand.

## Architecture

### Data layer

```
src/api/
  client.ts           # Axios instance — base URL from VITE_API_BASE_URL; sends the session cookie; a 401 returns to /login
  schema.d.ts         # generated by openapi-typescript — do not hand-edit
  endpoints/*.ts      # one file per resource (clients, accounts, sleeves, strategies, trades, admin, connections, performance)
src/hooks/            # one React Query hook per resource (useClients, useSleeves, useAdmin, ...)
```

Every endpoint has a thin typed wrapper in `src/api/endpoints/` and a matching hook in `src/hooks/`. Hooks are the only place TanStack Query is imported — feature components call hooks, not `apiClient` directly.

### State

Two React contexts drive all data-fetching:
- `ScopeContext` — the currently selected `{ clientId?, accountId?, sleeveId? }`. Changing scope invalidates performance queries.
- `DateRangeContext` — `{ startDate, endDate }` fed as query params to all performance endpoints.

Detail pages (client, account, sleeve) call `useScopeFollowsPage(...)` so the scope, and the top-bar breadcrumb that displays it, always names the entity on screen rather than whatever was last sent to Performance.

Both live in `src/context/`. Every performance screen reads from these; never accept scope or dates as local state.

### Routing

`/login`, `/invite/:token` and `/reset/:token` are open. Everything else sits under
`<RequireAuth role=…>` (`src/features/auth/RequireAuth.tsx`): the advisor workspace at `/app/*`,
**the new app at `/home/*`** (where a client lands after signing in). The old client portal is
retired: any `/portal/...` address opens the matching place in the new app (`OldPortalRedirect`
in `src/routes.tsx`), keeping an advisor's `?as=`.

**The new app (`/home`, `src/features/home/`)** is the 2026-11 redesign (designs in the local
`docs/design/one-app/`). `HomeShell` is the frame: a menu bar (the "achalara" wordmark is home;
Plan, Tax, Research), the person menu (Appearance, Manage for an advisor, Sign out), and on a
phone a bottom bar (Home, Plan, Tax, Research, More). `LandingPage` is an **account rail** plus
**view tabs**:
- The rail (`AccountRail`) lists the accounts in view (`/portal/accounts`), grouped by Person
  (only when more than one owner is in view), Kind (`account.kind`) or My groups
  (`/portal/groups`, edited in `GroupsDialog`, in an advisor's preview too: it is exactly what
  the client sees).
  Each account's figure, and every total built from them (the rail, the Dashboard's headline and
  kind tiles, the Accounts view), is `account.value`: the account now, exactly as the Holdings
  view's tile adds it up, so the two never disagree. The Dashboard says both clocks: the live
  prices' time (`priced_at`) and the day the custodian last reported holdings and cash (`as_of`).
- The selection and the open view live in the address, `?sel=all|owner:<id>|kind:<kind>|group:<id>|account:<id>&view=…`
  (`selection.ts`), and become `account_ids` on every portal request.
- Views: Dashboard (`DashboardView`), Accounts, Income and Analysis (`MoreViews.tsx`) are new;
  Holdings, Transactions, Performance and Cost basis are the portal's own pages, rendered inside
  `HomeSelection` (`portal/ui.tsx`), which narrows their account filter to the selection and
  hides their page titles. Views that cannot apply (Holdings for a cash account) are hidden.
- Plan and Tax are "coming soon" pages; Research is `ResearchPage` as built.
- An advisor opens it as a client with "Preview the new app" (`/home?as=<clientId>`).
- Screenshots for review: `ACHALARA_SESSION=<token> node scripts/screens.mjs <out> <route…>`
  saves each route at 390 and 1440 wide, light and dark (`playwright-core` with the installed Chrome).

`useMe()` (`src/hooks/useAuth.ts`) is the only source of who is
signed in; there is no auth context and nothing about the session is kept in `localStorage`.
`useLogin` / `useLogout` clear the query cache so one user's data is never shown to the next.

**The portal's pages** (`src/features/portal/`) now live only as tabs of the new app: Holdings
(`PortalHoldingsPage`: every account as an expandable tile, its strategies inside it, each
strategy's holdings inside that, from `/api/v1/portal/positions`), Transactions
(`PortalActivityPage`), Performance (`PortalPerformancePage`) and Cost basis
(`PortalRealizedPage`). Give sizes as explicit pixels (`p-[24px]`, `text-[16px]`) so the
spacing override below cannot change them. They read only `/api/v1/portal/*`
(`src/hooks/usePortal.ts`), where every percentage is a decimal fraction. Their own filters
(strategy, dates, type, an account within the selection) are local state on each page, not
`ScopeContext` / `DateRangeContext`, which belong to the advisor workspace. The realised-gains
page shows each lot as the custodian reports it (`cost`, `proceeds`, `short_term_gain`,
`long_term_gain`; `realized_gain` there is after any wash-sale loss, marked "W"); do not
recompute gains from entry and exit prices on the client. The holdings page is on live prices: it
shows `live_prices_at`, refetches every minute while open, and marks a row "custodian's price"
when `price_source` is `custodian`. An account's options are valued together at the custodian's
figure (`account_balances`), with cash beside them. The performance page's "Compare with" list
comes from the response (`benchmarks`); the choice is sent back as `benchmark`. Do not hard-code
benchmark names on a screen. An advisor previews a client's view at `/home?as=<clientId>`
("Preview the client's view" on the client's page); `usePreviewClient()` reads that, every
portal hook passes it on, and `HomeShell` keeps it on its links.

**Spacing classes:** `tailwind.config.ts` redefines the steps `4, 8, 12, 16, 24, 32, 48, 64, 96`
as that many pixels (`p-4` is 4px, `h-12` is 12px). Use `p-16` for 16px and so on; other steps
(`p-3`, `p-5`, `p-6`, `h-11`) keep Tailwind's defaults.

All advisor routes nest under `<AppShell>` at `/app/*`. Route params:
- `/app/clients/:clientId`
- `/app/clients/:clientId/accounts/:accountId`
- `/app/clients/:clientId/accounts/:accountId/sleeves/:sleeveId`

Fast-follower routes (`/app/portfolio`, `/app/risk`, `/app/grow`) exist but render `<ComingSoon>`.

### Data layer conventions

- **Field names must match the backend exactly.** Key ones: `mwr_pct`, `twr_pct`, `total_market_value`, `total_unrealized_gain` (on `PerformanceSummary`); `matched_quantity`, `entry_price`, `exit_price`, `opened_at`, `closed_at` (on `ClosedPosition`); `months` not `monthly_returns` (on `MonthlyReturnsResponse`).
- **Percentage units**: `mwr_pct`/`twr_pct`/`twr_cumul`/`mwr_cumul` are decimal fractions (0.05 = 5%); `unrealized_gain_pct`/`realized_gain_pct`/`return_pct` are whole-number percentages (7.34 = 7.34%). Pass decimals to `formatPercent`, whole numbers to display with `%` directly.
- **All IDs are UUIDs** (string, 36 chars) — never assume numeric.
- **Timestamps are ISO-8601 strings** in API responses.

### Navigation to PerformancePage

When navigating to `/app/performance` from a detail page, always wrap both the scope setter and `navigate()` in `flushSync()` to avoid React batching the state update after the page mounts:

```tsx
import { flushSync } from 'react-dom'
flushSync(() => setClient(id, name))
navigate('/app/performance')
```

This pattern is in `ClientsPage`, `ClientDetailPage`, `AccountDetailPage`, and `SleeveDetailPage`. Do not remove it — without it the performance page mounts before scope is set and renders blank.

### Performance chart date filtering

The backend always returns full-history `timeseries` regardless of `start_date`/`end_date` params. Filter on the client side before passing to `PerformanceChart` and `ReturnsSeriesChart`:

```tsx
data={perf.timeseries.filter(pt => {
  if (startDate && pt.date < startDate) return false
  if (endDate && pt.date > endDate) return false
  return true
})}
```

The quick-filter presets (`applyPreset`) set `DateRangeContext`; the chart section then re-filters from the already-fetched full series.

### Search boxes: choosing versus filtering

Sai's rule (2026-11-08): a box that **chooses one thing to load** (an index, a stock, a fund, a
benchmark) changes the page only on a decision, never while typing. Use
`research/SymbolPicker` (matches drop down as you type, a ticker column and a name column,
grouped, typed letters highlighted; Enter or a click chooses; a choice releases the cursor;
clicking back in clears the box; leaving it empty puts the choice back). The Performance page's
benchmark box follows the same rule by hand (Enter applies, Escape restores). A box that
**filters a list already on screen** (the portal's Holdings, Activity and Realised gains) stays
live as you type: nothing new loads, and clearing it on a click would throw the filter away.

### Formatters (`src/lib/formatters.ts`)

`shortAccountName` drops the owner names the brokerage puts in front of an account's name ("Pat Doe —
Roth IRA Brokerage Account" → "Roth IRA Brokerage"). Every screen names accounts this way:
`accountLabel` and `useAccountName` (`portal/ui.tsx`) add the owner's first name for an account
shared with the viewer, since the short name no longer says whose it is.

Central formatters for currency, percent, and dates — use these for every number that reaches the screen. All numbers render in `font-mono` with `font-feature-settings: "tnum"` (tabular figures), right-aligned in tables.

## Design Tokens

Custom tokens are in `tailwind.config.ts`; the ones that follow the theme get their values from
CSS variables in `src/index.css` (`:root` for light, `:root.dark` for dark). Brand rules that must hold:
- **Losses are clay, never red** — use `text-loss` / `bg-loss`, never `text-red-*`
- **Gold is the only accent** — one primary CTA per screen, highlighted figures
- **All numbers: `font-mono` + tabular figures** (`font-feature-settings: "tnum"`)
- **Gains: `text-gain`**

### Light and dark

**The new app and the sign-in pages honour the viewer's choice; the older screens stay dark.**
`ThemeContext` keeps a choice of Light, Dark or Auto (the device's setting, followed live) under
`achalara-theme`. A page of the new app calls `useOneAppLook()` (`HomeShell`, `AuthFrame`), which
puts `one-app` on `<html>` and applies the choice; everywhere else `THEME_CHOICE_OFFERED` (false)
keeps the advisor workspace dark as before. The script in `index.html` does the
same before first paint, by path (`/home`, `/portal`, `/login`, `/invite`, `/reset`, `/request-invitation`).
The choice is made under the person menu's Appearance (and on the sign-in page).

**The new look re-points the same tokens.** Under `:root.one-app` (and `.one-app.dark`) in
`src/index.css` the tokens below take direction C's palette (white or near-black page, violet
accent: `pine` and `gold` both become the accent, `pine-deep` a deep violet), so existing
components render in the new look without change. `gold`, `gain`, `loss`, `on-dark` and `on-gold`
are variables now (their old values are the defaults). New tokens, defined only under `.one-app`:
`line` (hairlines), `accent-soft`, and a colour and background per kind of account (`k-cash`,
`k-taxable`, `k-retire`, `k-kids`, each with `-bg`). Headings use Manrope there (`font-display`).
Charts in the new app take `useChartColours()`'s violet palette. The old tokens' values:

| Token | Use | Light | Dark |
|---|---|---|---|
| `paper` | the page | `#FBFCFB` | `#1E3A2F` |
| `surface` | cards, inputs, tables | `#FFFFFF` | `#264739` |
| `mist` | tinted panels | `#EAF0EC` | `#305646` |
| `summit-ink` | body text | `#14201C` | `#EEF3F0` |
| `stone` | secondary text, hairlines | `#8A968F` | `#ACBBB3` |
| `chrome` | header, sidebar (dark in both) | `#14201C` | `#0D1814` |
| `on-dark` | text on chrome, pine, gain/loss fills | `#FBFCFB` | same |
| `on-gold` | text on a gold button | `#14201C` | same |
| `pine-deep` | the headline card and sign-in panel (light); a hovered button | `#1E3A2F` | `#356650` |
| `pine` | buttons, the selected pill | `#2F5D4A` | `#427E65` |
| `gain`, `loss`, `gold` | fills | `#2E8B6B` `#C2703D` `#C9A24B` | same |

Rules that keep both themes working:
- **Never `bg-white` or `text-white`**: use `bg-surface` and `text-on-dark`.
- **`text-summit-ink` flips**, so do not put it on a fill that stays the same in both themes:
  on gold use `text-on-gold`; on `chrome`, `pine`, `pine-deep`, `bg-gain`, `bg-loss` use `text-on-dark`.
- `text-pine`, `text-pine-deep`, `text-gain`, `text-loss` and `border-pine` are lighter in dark
  (set under `textColor` / `borderColor` in the config); the `bg-*` of the same names are not.
- **Charts take colours from `useChartColours()`** (`src/context/ThemeContext.tsx`), not from
  hex literals: Recharts writes into SVG attributes, where CSS variables do not resolve.
- The marketing page (`features/HomePage`) is dark in both themes. Its top bar has "Sign in"; the way in for someone new is "Request an invitation".
- In dark the page is the brand's mid green; the near-black green is for `chrome` only.
- **The headline card** (`<Card dark>`, `StatCard highlight`): a dark-green card in light mode;
  in dark mode an ordinary card with a gold outline (`dark:bg-surface dark:border-gold/70`).
- **Restart `npm run dev` after editing `tailwind.config.ts`.** The dev server keeps serving the
  old colours otherwise, which looks like a half-applied theme.

## What "Done" Looks Like

- Component reads from a hook, not raw `apiClient`
- `isLoading` → `<Skeleton>`, `isError` → `<ErrorState>` with retry, empty → `<EmptyState>`
- Numbers formatted via `src/lib/formatters.ts`, gains green, losses clay
- No mock data in committed paths once the real endpoint works
- `openapi.yaml` updated if a new endpoint was added
